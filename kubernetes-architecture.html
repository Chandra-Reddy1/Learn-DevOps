End-to-End Request Flow · kubectl apply -f deployment.yaml
Master
STEP 01
kubectl → API Server
User runs kubectl. Request hits kube-apiserver via HTTPS. Auth + RBAC check happens.
Master
STEP 02
API → etcd Write
Desired state (3 replicas of nginx) is persisted to etcd. Source of truth updated.
Master
STEP 03
Scheduler Watches
Scheduler notices unbound pods via watch. Scores nodes by CPU/RAM/affinity rules.
Master
STEP 04
Binding Recorded
Scheduler writes pod→node binding back to etcd via API server. Pod is now "assigned".
Worker
STEP 05
kubelet Detects
Worker's kubelet watches API server. Sees pod assigned to its node. Begins pod creation.
Worker
STEP 06
Container Starts
kubelet calls containerd. Image pulled from registry. Container network & volumes attached.
Worker
STEP 07
kube-proxy Updates
kube-proxy updates iptables/ipvs rules. Pod IP registered with Service endpoint.
Master
STEP 08
Controller Watches
ReplicaSet controller reconciles. Pod crashes? Instantly creates replacement. Loop never stops.
Component Deep Dive · What it does + Real-time Scenario
Control Plane
Worker Node
🚪
kube-apiserver
// REST Gateway · Validation · Authentication
The single entry point for all control plane operations. Every kubectl command, every controller watch, every kubelet heartbeat — all go through this RESTful API. It validates objects, enforces RBAC policies, and writes approved state changes to etcd. It also serves as the communication hub between all other control plane components.
Real-Time Scenario
Your DevOps engineer runs kubectl scale deploy/checkout --replicas=10 during Black Friday traffic surge. API server authenticates the token, checks RBAC (can this user patch deployments?), validates the object schema, then commits the new desired state to etcd — all in under 100ms.
💾
etcd
// Distributed KV Store · Source of Truth
A consistent, highly-available key-value store that holds the entire cluster state — every pod, node, config, secret, and service definition. It uses the Raft consensus algorithm to maintain consistency across replicas (usually 3 or 5 instances). All reads and writes from the control plane go through here. If etcd dies, the cluster can no longer make decisions (though running workloads continue).
Real-Time Scenario
A node goes offline at 3AM. etcd already has the last known state of all pods running on that node. The controller-manager reads from etcd, detects missing pods, and immediately orchestrates replacements — all without human intervention.
📋
kube-scheduler
// Pod Placement · Resource Scoring
Watches for newly created pods with no assigned node and selects the best node for them to run on. It uses a two-step process: filtering (which nodes meet hard requirements — resources, taints, nodeSelectors?) and scoring (which filtered node is the best fit using priority functions). It then binds the pod to the winning node.
Real-Time Scenario
A new ML training pod requests 4 GPUs and 32GB RAM with a node-type: gpu nodeSelector. Scheduler filters out all 12 CPU-only workers, scores the 2 GPU nodes by available capacity, and places the pod on Worker-03 which has 40GB free — in milliseconds.
🔄
controller-manager
// Control Loops · Self-Healing · Reconciliation
Runs multiple controllers in a single process. ReplicaSet controller ensures the right number of pods exist. Node controller handles node failures. Deployment controller manages rolling updates. Job controller runs batch tasks to completion. Each controller watches cluster state and continuously reconciles actual state to match desired state — this is the "self-healing" magic of Kubernetes.
Real-Time Scenario
A developer accidentally deletes a pod from the payment service. Within 2 seconds, the ReplicaSet controller detects the count is 2 instead of 3, creates a new pod spec, and kube-scheduler places it. By the time anyone opens Slack to report the issue, the pod is already Running. 🔥
☁️
cloud-controller-manager
// Cloud Provider Integration
Abstracts cloud provider-specific logic (AWS, GCP, Azure) from the core Kubernetes codebase. It handles provisioning cloud load balancers when you create a Service of type LoadBalancer, managing cloud storage volumes for PersistentVolumeClaims, and updating routes in cloud VPC networks when new nodes join.
Real-Time Scenario
You apply a Service with type: LoadBalancer on AWS EKS. The cloud-controller-manager automatically calls the AWS EC2 API, provisions an Application Load Balancer, configures target groups pointing to your worker nodes, and writes the external IP back to your Service object — zero manual AWS console work.
🤖
kubelet
// Node Agent · Pod Lifecycle Manager
The primary node agent running on every worker. It registers the node with the API server and continuously watches for pods assigned to its node. It talks to the container runtime (containerd/CRI-O) to start, stop, and manage containers. It also runs liveness and readiness probes and reports pod status back to the control plane every few seconds.
Real-Time Scenario
A pod's liveness probe (HTTP GET /healthz) returns 500 three consecutive times. kubelet automatically kills the container and restarts it — exactly as configured in livenessProbe.failureThreshold: 3. Your users experience zero downtime during this restart because kube-proxy continues routing to healthy pods.
🌐
kube-proxy
// Network Rules · Service Routing
Runs on every node and maintains network rules (iptables or IPVS) that enable the Service abstraction. When a pod sends traffic to a ClusterIP service, kube-proxy's rules transparently forward it to one of the healthy backend pod IPs. It watches the API server for Service and Endpoints changes and updates rules in real-time.
Real-Time Scenario
Your frontend calls http://order-service:8080. This DNS resolves to ClusterIP 10.96.50.10. kube-proxy's iptables rules DNAT the packet to one of 5 available order-service pod IPs (load balanced via random selection). If a pod dies, kube-proxy removes its IP from rules within seconds — no stale routing.
📦
Container Runtime
// containerd · CRI-O · Image Pull · Execution
The software responsible for running containers on the node. Kubernetes uses the Container Runtime Interface (CRI) to talk to any compliant runtime. containerd (default in most managed clusters) handles image pulling from registries, unpacking them as overlayFS layers, setting up namespaces, cgroups, and seccomp profiles, and running the actual container process.
Real-Time Scenario
A new release of your API (v3.2.1) is deployed. containerd pulls only the changed Docker layers from ECR (not the whole image — layer caching!), sets up a new PID namespace and network namespace, mounts the volume, and starts the process with CPU/memory cgroup limits of 500m / 512Mi as requested.
🫙
Pod
// Smallest Deployable Unit · Shared Network + Storage
A pod is the atomic unit of Kubernetes. It can contain one or more tightly coupled containers that always run together on the same node, share the same network namespace (same IP, can communicate via localhost), and can share volumes. Pods are ephemeral — when they die, they don't come back. Controllers (ReplicaSets, Deployments) manage pod lifecycle.
Real-Time Scenario
Your main app container + an Envoy sidecar proxy run in the same pod. The app writes to /var/log/app.log. A log-forwarder container in the same pod reads that file (shared volume) and ships to Elasticsearch. They share an IP — Envoy intercepts traffic on port 15001 transparently. This is the Istio service mesh sidecar pattern.
🔌
CNI Plugin
// Pod Networking · Calico / Flannel / Cilium
The Container Network Interface plugin handles assigning IP addresses to pods and setting up network routes between pods across different nodes. Flannel uses VXLAN overlays, Calico uses BGP for routing, and Cilium uses eBPF for high-performance packet processing. Every pod gets its own IP and can reach any other pod in the cluster directly.
Real-Time Scenario
Pod A on Worker-01 (10.244.1.5) calls Pod B on Worker-03 (10.244.3.12). Cilium's eBPF program intercepts the packet at kernel level, looks up the route in its distributed map, and tunnels it across nodes — all without touching iptables, achieving 3x the throughput of kube-proxy for high-RPS microservices.
💽
CSI / Volumes
// Persistent Storage · PV · PVC
The Container Storage Interface allows storage vendors to write plugins for Kubernetes. PersistentVolumes (PV) are cluster-wide storage resources. PersistentVolumeClaims (PVC) are pod requests for storage. The CSI driver handles dynamic provisioning — creating cloud disks (EBS, GCE PD) on demand, mounting them to the right node, and presenting them as a directory inside the container.
Real-Time Scenario
Your PostgreSQL pod claims a PVC of 100GB SSD. The AWS EBS CSI driver creates a gp3 EBS volume in the same AZ as the worker node, attaches it via nvme, formats it as ext4, and mounts it at /var/lib/postgresql/data. When the pod is rescheduled to another node, the volume detaches and reattaches automatically — zero data loss.
